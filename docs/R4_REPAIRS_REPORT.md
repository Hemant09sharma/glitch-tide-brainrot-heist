### Bugs found by the tests during R4 (and fixed)
- **R4-1 live-ledger marking:** `invalidateStaleReturnEscrow` only created a `ReturnedTxns` marker when none existed; the victim's ledger already held the return entry from the retries, so `Superseded` was never set on it. ## 4. Remaining risks — stated plainly

### Policy change (R4-4) — documented, not a bug
R3 paid a pending reward even when its delivery was voided on rejoin. **R4 reverses this: reward eligibility follows the delivery transaction's durable fate.** A delivery that is voided during recovery has its reward cancelled/refunded idempotently; a durably committed delivery keeps exactly-once reward recovery. This is the specified R4-4 outcome. The R3 report's "Policy split (flagged, not fixed)" is now resolved in favour of voiding the reward with the delivery.

### Open durability windows (the honest limits)
- **R4-2 W4-analog (loss, narrowed not closed):** if the sidecar park fails AND the server crashes before any main save succeeds, the reward exists only in cache and is lost (durability needs at least one key to accept a write). Park retry narrows the window — the park is now retried on every recovery, rejoin and leave — but cannot close it.
- **R4-1 residual race:** `ConfirmDelivery` vs `ReturnStolen` interleaving via yields inside `ConfirmDelivery` is a pre-existing race (not introduced by R4-1), but R4-1's invalidation read adds a yield point — mitigated by the post-invalidation re-verification of `_inTransit` and ownership (a return landing during the yield wins).
- **R4-3 FusionService gap (CLOSED in follow-up):** the last direct-assignment debit (`FusionService.luau:283`, refund :291) now goes through `DataService.AddCoins` with a spendable-coins affordability check; test 10 covers it (8 checks) with a negative control proving the old code fails exactly the 4 reservation-related fusion checks (40/44). Removed from the open list.
- **R4-7 partition limit:** a failed lease read falls back to the cached lease, so two servers could both save during a `GetAsync` outage. Lease TTL 90 s means a crashed server's lease can delay a clean rejoin by up to ~90 s.
- **R4-8 shutdown wall-clock budget is not measurable in Lune:** `task.wait` returns 0 immediately and `task.spawn` is discarded by the harness stub (it only increments `spawnCount`), so the parallel-vs-sequential bound cannot be observed end-to-end in tests. Test 07 proves the structural properties (one spawn per player, bounded return, no inline sequential saves) + the synchronous per-player unit for 12 players, and the bound argument is documented in the code (parallel ≈ slowest single save; sequential ≈ sum). A Studio shutdown test with 12 players under a degraded store is still required.
- **R4-6 TxId fallback:** if `HttpService:GenerateGUID` is unavailable, the fallback is the old probabilistic shape + a `math.random` suffix — probabilistic only. No cryptographic guarantee is claimed beyond what GenerateGUID provides.
- **R3-5 W4 (unchanged):** sidecar park fails *and* crash before any main save succeeds → reward lost. R4-2 narrows it (retry) but the window is the same shape.
- **R3-6 W4-analog (unchanged):** escrow park fails *and* victim save fails *and* thief-side deletion persists *and* crash before any retry → 0 owners.
- **R3-6 residual D (CLOSED by R4-1):** the 5-condition duplication scenario is now fixed and tested (test 01). Removed from the open list.
- **R6 save reliability is NOT claimed fixed.** Delivery saves are observed and warned on, but crash windows remain: a crash after commit but before any save still loses the in-memory commit for non-ledgered state (ordinary earnings, XP, unlocks — up to one 60 s autosave interval). The reconciler voids an unpersisted delivery conservatively (victim gets the Brainrot back, thief keeps nothing) and a delivered-but-unsaved steal reward is lost, never re-minted. That is the conservative exactly-once choice, not a durability guarantee.
- **Load-failed durability hole (narrowed, not eliminated):** sidecars mitigate but do not eliminate it — a crash between sidecar merge and a successful save re-merges safely, but a player who never achieves a successful load still has no durable record. `_loadFailed` sessions play on defaults with saves refused by design (protects the real save); a player who plays a full session on a failed load loses everything earned in that session. **New in R4:** the player now sees a persistent client-facing `SaveWarning` banner (R4-8) instead of only a server `warn`.
- **Cost note (unchanged from R3, one addition):** every healthy delivery now does a sidecar `UpdateAsync` (park-first) plus a *synchronous* `SaveData` on the delivery path (previously fire-and-forget), and R4-1 adds one escrow `UpdateAsync` (tombstone) per delivery when a stale return exists for the instance (no-op read when none exists — the read is a `GetAsync` via `readSidecar`, which retries twice). Production latency impact not measured.
- **Cross-server behaviour is still unproven live.** The lease is now tested in simulation (two module instances sharing one stub store); real multi-server Roblox behaviour is not tested.
- **No Studio playtest or real production DataStore test** has been run against any of this. All verification is Lune/harness-level with a stubbed DataStore API that models the contract.

### Harness limits that bound what the tests prove (not product bugs)
- **Conveyor `BuyItem` is not live-testable under Lune:** `BuyItem` locates the item via the world model, and Lune's `typeof()` returns `"table"` for the harness's mock Instances (it ignores the `__type` metatable field — verified by probe), so `typeof(model) == "Instance"` is never true and `itemPos` is always nil → every buy is refused as "too far" before the affordability check. Test 10 proves the refusal charges nothing and the item stays listed; the affordability check is asserted by the `GetSpendableCoins` static anchor in `run.sh`. The route's spendable-check code is identical in shape to the five routes proven live.
- **HUD `SaveWarning` client behaviour is not Lune-testable** (no client harness): verified by server-side payload + static anchors + luau-compile; Studio playtest still required.
- **Shutdown fan-out completion is not observable in Lune** (product modules' `task.spawn` calls bypass a test-file override — Luau fastcall, verified by probe). Test 07 proves structure + the synchronous per-player unit only.
- **Two-server tests load the same `DataService` source twice under different module paths** (second copy `DataServiceB.luau` in the r4 suite) sharing one stub store — separate `_serverId` + module state per copy. This models server identity, not real Roblox server processes.
