# Persistence Design Note — GLITCH TIDE DataStore model (post-R4)

**Scope:** how player data, theft transactions, steal rewards and returns are persisted, what is durable, and what is not. Companion to `docs/R4_REPAIRS_REPORT.md` (and `docs/R3_REPAIRS_REPORT.md`). No economy change is described here; the N5 banked-income design (`docs/N5_BANKED_INCOME_DESIGN_NOTE.md`) remains a proposal only.

## 1. Keys and what lives where

| Key (per `UserId`) | Contents | Writer |
|---|---|---|
| Main profile (`Player_<UserId>`) | The whole player data table: coins, XP, owned Brainrots, base, quests, `PendingRewards` (in-cache ledger), `ProcessedRewardTxns`, `ReturnedTxns`, `VoidedRewardTxns` (R4-4), `VoidedRewardInstances` (R5-3: instance-level void ledger, see §5b), `StolenFromUserId`/`Stolen*` fields on moved records | `DataService.SaveData` (the single save owner) |
| Escrow sidecar (`Brainrot_Escrow_<UserId>`) | List of parked Brainrot records awaiting return to an offline victim, plus parked return transactions (`ReturnTxId`), plus delivery tombstones (R4-1: `{Superseded=true, SupersedesReturnTxIds, ...}`) | `DataService.EscrowReturnedInstance` / `ParkReturnEscrow` / `InvalidateReturnEscrow` via `appendSidecar` |
| Pending-reward sidecar (`Pending_Rewards_<UserId>`) | List of pending steal-reward entries, each with a TxId and a delta amount, plus reward-void entries (R4-4: `{Voided=true, VoidTxId, TxId="void-<txId>"}`) and instance-level void tombstones (R5-3: `{Voided=true, VoidInstance=true, TxId="void-inst-<InstanceId>"}` — see §5b) | `DataService.RecordPendingRewardSidecar` / `RecordRewardVoidSidecar` / `RecordRewardVoidForInstance` via `appendSidecar` |
| Session lease (`Brainrot_Session_<UserId>`) | `{ServerId, AcquiredAt, ExpiresAt}` — which server owns this player's mutable profile right now (R4-7, TTL 90 s) | `DataService` lease functions via `UpdateAsync` (never `SetAsync`) |

**Rule: the main profile is the only key whose write is a full-table `SetAsync`.** Sidecars are append-only lists mutated exclusively through `appendSidecar` (`UpdateAsync`). Nothing else writes the sidecar keys.

## 2. Invariants

1. **Exactly one owner per `InstanceId` after recovery.** Enforced by `RecoverStaleTransit` rules (a)–(d) on rejoin plus the escrow/return markers. Rule (e) — a flagged record with no recorded owner — stays flagged forever rather than being deleted or granted; that is deliberate.
2. **A reward transaction pays at most once.** Enforced by the TxId + `ProcessedRewardTxns` ledger (see §4), not by the sidecar's presence or absence.
3. **A return transaction restores at most once.** Enforced by the `ReturnedTxns` ledger + `mergeEscrowRecord` marker-skip (see §5).
4. **A failed read never destroys data.** `readSidecar` returns `(ok, value)`; a failed read aborts the operation. There is no `or {}` anywhere in the sidecar paths.
5. **No side effects inside an `UpdateAsync` callback.** The transform is a pure function of the old value (copy, dedupe, append/replace). Rewards are never paid inside a callback.
6. **Single save owner.** `DataService` owns all saves. `RegisterPreSaveHook` lets services run recovery *before* the leave/shutdown save; `GameManager`'s competing `onPlayerRemoving` and second `BindToClose` were removed in R2-5. `ReturnStolen` never saves inside the pre-save hook (`_preSaveHookDepth`).

## 3. Sidecar appends (R3-1 / R3-2)

- **Read:** `readSidecar` tries `GetAsync` twice (0.5 s apart) and returns `(true, table | nil)` on success (nil = key genuinely empty) or `(false, nil)` on failure. Callers must branch on `ok`; a failed read aborts the append and the merge, and leaves the entry parked for retry.
- **Append:** `appendSidecar(store, key, entry, combine?)` runs `store:UpdateAsync(key, transform)`. The transform copies the stored list, dedupes by identity, and either keeps the existing entry (escrow: pure no-op on duplicate) or replaces it with `combine(existing, entry)` (pending rewards: fresh deep copy with `Amount` summed — the stored entry is never mutated in place, so a retried callback stays deterministic). Two attempts with 0.5 s between; safe to retry because the operation is idempotent per identity.
- **Identity:** `sidecarIdentity(entry)` is the TxId when present, else `legacy:<InstanceId>:<CreatedAt>`. Escrow entries have neither, so their identity is the `InstanceId` (pre-R3 rule, unchanged).
- **Delete:** `deleteSidecar` returns a real boolean. `SaveData` deletes each sidecar key only when its load-time read succeeded, one at a time, clearing each flag only on successful delete; a failed delete stays flagged for the next save.

## 4. Steal rewards — transaction model (R3-3 / R3-4 / R3-5)

### Transaction identity
Every successful delivery/reward event mints one TxId at `grantStealReward` time (R4-6):
`sr-<guid>-<thiefUserId>-<instanceId>-<perServerCounter>`, where `<guid>` is `HttpService:GenerateGUID(false)` (128-bit random, server-independent). A Brainrot stolen and delivered twice gets two TxIds. A retry of the same transaction keeps the same TxId. Fallback if GenerateGUID is unavailable: the old `sr-<user>-<instance>-<unix>-<clockMs>-<counter>` shape + a `math.random` suffix (probabilistic only, with a warn). No cryptographic guarantee is claimed beyond what GenerateGUID provides.

### Ledger shape
- **In-cache aggregate** `data.PendingRewards`, keyed by `InstanceId`: `{InstanceId, CharacterId, Amount, Reason, CreatedAt, Txns = {[TxId] = delta}}`. `Amount` is the sum of its not-yet-paid recordings. A legacy entry (no `Txns`) normalises to one implicit transaction `legacy-<InstanceId>-<CreatedAt>`.
- **Sidecar entry:** `{TxId, InstanceId, CharacterId, Amount = delta, Reason, CreatedAt}` — one entry per recording, never an accumulated total.
- **Processed ledger** `data.ProcessedRewardTxns[TxId] = {TxId, InstanceId, Amount, PaidAt}`, persisted in the main profile. It is never pruned (one small entry per paid reward); stale sidecar entries self-clean on the next load + save.

### Semantics — delta model (R3-4)
Each `recordPendingReward` call is one recording: its **delta** is added once to the in-cache aggregate and the **same delta under the same TxId** is parked in the sidecar. Re-recording the same TxId is a replay and is a no-op in both places; a new TxId for the same instance is a new transaction and adds its delta. The old bug was the mixed model (cache accumulated, then the sidecar accumulated the already-accumulated total: 100 then +150 → 350 instead of 250).

### Commit protocol (`commitPendingPayment`)
1. AddCoins + marker insertion + pending-entry removal happen in the **one in-memory data table**.
2. One synchronous `SaveData` (one `SetAsync`) persists all three together.
3. On save failure, roll back in memory (un-pay first, then un-mark, then restore the entry) and return pending — the sidecar entry parked first is the durable backstop.
4. `RecoverPendingRewards` routes every entry through this commit and counts only coins actually paid (`commitPendingPayment` returns `(boolean, amountActuallyPaid)`).

### Delivery path (`grantStealReward`)
Mint TxId → record pending (park-first sidecar write) → verified commit. The reward is **not** considered durably paid merely because `AddCoins()` succeeded in memory. The formula is unchanged: one computation via `Economy.StealReward` / `Economy.StealRewardShare` (configured multiplier + rarity bonus).

### Crash windows
| Window | State |
|---|---|
| Crash after sidecar park, before pay/save | Closed — sidecar holds the entry, profile has no marker → rejoin merges and pays once. |
| Crash after in-memory pay, before save completes | Closed — stored profile never saw the payment. |
| Every save fails | Closed — commit rolls back to pending; sidecar is the backstop; rejoin recovers exactly once. |
| Sidecar park itself fails **and** crash before any main save succeeds | **OPEN (W4) — narrowed by R4-2, not closed** — the park is now retried on every recovery, rejoin and leave (`RetryPendingParks`, same TxId, idempotent), so the reward survives any window in which the server stays up long enough for one retry to land. Lost only if the crash comes before any retry succeeds. Durability needs at least one of the two keys to accept a write. |
| Cross-key atomicity | **Limit (W5)** — coin change + marker are atomic only within the main profile key. The sidecar is a separate key; a stale sidecar entry can linger after a durable pay (neutralised by the `ProcessedRewardTxns` check on re-merge, deleted on the next load + save). Two servers writing the same player's main key can still last-write-win. |

### Policy note (R4-4 — reverses the R3 policy)
When every save fails, the delivery itself is voided on rejoin (R2 rule: no durable proof → no ownership) **and the reward is now cancelled with it**. Reward eligibility follows the delivery transaction's durable fate: a voided delivery's pending TxIds are recorded in `data.VoidedRewardTxns` (durable, via `RecordRewardVoidSidecar`) and can never be paid, on any rejoin; a durably committed delivery keeps exactly-once reward recovery. The R3 policy (pay the reward for a voided delivery) is superseded. **R5-3 durability (see §5b / R5 addendum):** the void no longer depends on the reward being in the in-memory `PendingRewards` table or on a successful pending-sidecar read — it parks a durable instance tombstone (`void-inst-<InstanceId>`) in the pending sidecar plus the `VoidedRewardInstances` ledger in the main profile, and an unpersistable void stays pending for retry (`_pendingVoids` + `RetryPendingVoids`) instead of silently finishing the recovery.

## 5. Returns — transaction model (R3-6)

### The return transaction (park → commit → verify)
1. **Park:** immediately *after* the in-memory move succeeds, park the full-fidelity return in the victim's escrow sidecar under a fresh `ReturnTxId` (`rt-<guid>-<victimUserId>-<instanceId>-<perServerCounter>`, R4-6 GUID). Parking before the move would leave a return claim parked for a record the thief still holds if the move then failed. The park also heals the steal's own loss window.
2. **Commit (in memory):** clear theft markers; record the TxId in the victim's `data.ReturnedTxns` ledger (`{TxId, InstanceId, ReturnedAt}`) in the same data table as the returned record; clear transit/carry; clear the orphaned expedition flag; reinsert the placed copy with full fields (slot, original `PlacedAt`, `BankedIncome`, Mutation, Evolved fields, `TraitLevels` copied).
3. **Verify:** `saveVerified(victim)` persists record + placed copy + marker together; `saveVerified(thief)` is best-effort (a stale `InTransit` copy in the thief's key is deleted by rejoin rule (b) — the victim holds the clean copy — or by the thief's next autosave). On victim-save failure: keep `_inTransit[instanceId]` so the 5 s watchdog retries the return (re-park + re-verify; the in-memory return stands, so no rollback and no delivery hazard), skip the thief's save so the thief's stored `InTransit` copy survives as the rejoin backstop. Retries bounded at 3 (`record.ReturnSaveRetries`); after that the escrow park + the victim's autosave/leave-save are the backstops.
4. `ReturnStolen` returns **durability**, not just "in-memory committed" — `false` when the victim's verified save fails. (In the pre-save-hook path no save is attempted, so it still returns `true` there.)

### Marker
`DataService.mergeEscrowRecord` skips an escrow entry whose `ReturnTxId` is already in `data.ReturnedTxns`, and records the TxId there when it applies or dedupes an entry. This stops a stale escrow entry from voiding a legitimate re-steal.

### Recovery order on rejoin
Load (merge sidecars — escrow applied unless the marker skips it, marker recorded) → `RecoverOnRejoin` → `RecoverStaleTransit`: (a) placed copy in own base proves delivery → clear markers; (b) another online player holds a clean copy → delete the stale copy; (c) this player IS the recorded owner → restore from `Stolen*` fields; (d) victim offline → `tryEscrowReturn` re-parks (replace, fresh TxId) and destroys the thief's record. **R5-3 void-retry-first:** `RecoverPendingRewards` and `RecoverOnRejoin` both call `RetryPendingVoids` before any payment, so a void that failed to persist on an earlier recovery is re-attempted with the same stable identifiers before anything can pay (see §5b / R5 addendum).

### Crash windows
| Window | State |
|---|---|
| Steal-time victim save lands, thief hold save never lands, crash before the 120 s autosave (the original hole) | Closed — park + verified save + marker. |
| Victim save fails | Closed — escrow + bounded retry. |
| Thief save fails | Closed — rule (b) deletes the stale copy. |
| Both saves fail | Closed — escrow alone recovers. |
| Victim offline | Closed — escrow + re-park on thief-first rejoin. |
| Repeated crash → rejoin | Closed — idempotent. |
| Stale escrow vs re-steal | Closed — marker skip. |
| Escrow park fails **and** victim save fails **and** thief-side deletion persists **and** crash before any retry | **OPEN (W4-analog, confirmed by scratch D4a)** — 0 owners. Needs a partial outage (victim key + escrow fail, thief key succeeds); in a total outage all saves fail, so the thief's stored `InTransit` copy survives and rule (d) recovers. |
| Victim save fails → Brainrot re-stolen and delivered → victim leaves/crashes before ANY victim save lands the marker → victim rejoins | **CLOSED by R4-1** — the delivery parks a tombstone in the victim's escrow sidecar (see §5a) that supersedes the stale return; `mergeSidecars` refuses it. Tested by r4-transactions test 01 (Qwen's exact five-condition scenario); the old code duplicates (mutant m01). |

## 5a. Delivery tombstones (R4-1)

A later successful delivery must invalidate/supersede all older return escrow transactions for that `InstanceId`, even when the original victim is offline — the `ReturnedTxns` marker alone cannot do this, because it exists only in the victim's unsaved memory when the victim's save failed.

- `ConfirmDelivery` mints `deliveryTxId` (the same id the reward grant names) and calls `DataService.InvalidateReturnEscrow(victimUserId, instanceId, deliveryTxId)` BEFORE the delivery commits. `InvalidateReturnEscrow` reads the victim's escrow sidecar, collects every return entry for the instance (TxIds + whether any legacy entry without a `ReturnTxId` exists), and parks one tombstone `{Superseded=true, SupersedesReturnTxIds={...}, SupersedesLegacy=bool, DeliveryTxId, SupersededAt, TxId="sup-<deliveryTxId>"}` via `appendSidecar`. The tombstone's TxId keeps its identity distinct from return entries (no TxId) and other tombstones.
- `mergeSidecars` processes tombstones FIRST: superseded TxIds are recorded in `data.ReturnedTxns` (with `Superseded=true`), so the existing marker-skip in `mergeEscrowRecord` refuses the stale entry; the tombstone itself is never merged as a record; legacy (no-`ReturnTxId`) entries are skipped when a tombstone has `SupersedesLegacy`. Unrelated escrow entries are preserved.
- If the invalidation cannot be persisted (read or append fails), the delivery is refused fail-closed: transit stays live, no reward is paid, `PlaceBrainrot` aborts the placement with no state change, and the thief keeps carrying and can retry. The invalidation yields on DataStore calls, so the theft is re-verified afterwards (`_inTransit` + ownership) — a return landing during the yield wins.
- **R5-5 no-store fail-closed rule (see R5 addendum §5a):** a missing/unavailable store is NOT an empty sidecar. When `GetDataStore` fails to provide a usable store, `InvalidateReturnEscrow` returns `(false, false, "datastore unavailable", nil)` — the delivery is refused exactly as for any other unpersistable invalidation. The old branch returned success without reading anything, which let a delivery commit while a stale return the server could not see still existed in the victim's sidecar.
- Repeated delivery/return/rejoin/retry is idempotent: a tombstone for an already-superseded TxId re-parks harmlessly (same identity, deduped by `appendSidecar`); a second delivery mints a fresh `deliveryTxId` and parks a fresh tombstone.

## 5b. Reward voids (R4-4)

See §4 policy note. Mechanically: `voidPendingRewardsForInstance` voids all NOT-YET-PAID pending TxIds for an instance (already-processed TxIds are never voided — a paid reward implies its delivery commit saved marker+coins+flag-clear together), records them in `data.VoidedRewardTxns`, parks void entries `{Voided=true, VoidTxId=txId, TxId="void-<txId>"}` in the pending sidecar (the `void-` prefix keeps append identity distinct from the reward entry with the same TxId), and removes the pending entry. It is called only when recovery actually resolves the theft back to the victim: `RecoverStaleTransit` rule (b) and rule (d). `mergeSidecars` processes void entries first: records TxIds in `VoidedRewardTxns`, drops voided TxIds out of in-cache pending entries (adjusting Amount, removing the entry if empty), and skips merging reward entries whose TxId is voided or processed. `commitPendingPayment` never pays a voided TxId.

**R5-3 durability (see R5 addendum §5b):** the void no longer depends on the reward being in the in-memory `PendingRewards` table or on a successful pending-sidecar read. `voidPendingRewardsForInstance` (RaidService 2762) never early-returns on a missing cache entry; `persistVoid` (2727) parks a durable instance tombstone `void-inst-<InstanceId>` via `DataService.RecordRewardVoidForInstance` (1591) as leg 1 and persists the `VoidedRewardInstances` / `VoidedRewardTxns` ledgers with a main-profile save as leg 2 — durable iff either leg lands. `mergeSidecars` (1156; void handling ~1257–1361) processes tombstones first: it records the instance in `data.VoidedRewardInstances`, drops every TxId of that instance out of in-cache pending entries, and refuses every later reward entry for the instance. An unpersistable void is kept in the in-memory `_pendingVoids` table and retried with the same stable identifiers (`RetryPendingVoids`, 2846) before any payment; a recovery whose void is not durable counts the instance `remaining`, not `resolved`. `commitPendingPayment` (guard ~678) also refuses TxIds of a voided instance even when the void never named the TxId. Residual window (narrowed, not closed): a void whose tombstone AND fallback save both fail AND the server crashes before any retry is the W4-analog — durability needs at least one key to accept a write.

## 6. Save ownership, session lease and shutdown (R4-7 / R4-8)

- `DataService` is the single save owner. Pre-save hooks run before the leave/shutdown save; `GameManager`'s competing handlers were removed in R2-5.
- **Session lease (R4-7, corrected by R5-4 — see R5 addendum §6).** Only one active server owns a player's mutable profile. Lease key `Brainrot_Session_<UserId>` = `{ServerId, AcquiredAt, ExpiresAt}`, TTL 90 s. `acquireSessionLease` via `UpdateAsync` pure transform (keeps a live lease owned by another server; takes free/expired/own). `checkSessionLease` gates `SaveData`: ownership is verified against the STORED lease on every check; a positive sighting of another live owner blocks the save and sets `_sessionLost`. **A failed lease read no longer falls back to the cached lease** (the R4 partition limit is closed this way): the failed read is resolved by an atomic proof — the same conditional `UpdateAsync`, whose RESULT names the owner. This server proving ownership lets the save proceed; another live owner proves loss (sticky `_sessionLost`); a failed proof refuses THAT save attempt only and never poisons the session (recorded in `_leaseCheckUnverified`, cleared on `PlayerRemoving`). The local cached expiry is extended only when an `UpdateAsync` result confirms this server owns the lease (`refreshSessionLease` is result-checked and returns bool). `SaveData` revalidates the lease after the `_saving` wait and immediately before every `SetAsync` retry. `GetSessionLeaseState` exposes `{Owned, Contested, Lost, ServerId, LeaseExpiresAt, LastLeaseCheckFailed}` for the R5-2 gates and diagnostics (`Owned` is a local view only and never authorises a write by itself). A successful save refreshes the lease. `ReleaseSessionLease` deletes only when the lease is still ours. `LoadData` acquires the lease only on successful load; failure ⇒ `_loadFailed` (R5-1) and the session is unsaveable, and a contested lease ⇒ `_sessionContested` (set only in `finishSuccessfulLoad`'s lease path), skips daily bonus + sidecar merge. `GetSaveBlockedReason` returns nil / `"load_failed"` / `"session_contested"` / `"session_lost"`; `IsSaveable` is false for contested/lost as well as load-failed; `SaveData` refuses when contested/lost. PlayerRemoving clears lease/contested/lost/reserved/lease-cache flags; BindToClose releases leases after saves. A crashed server's lease expires on its own (≤ 90 s) — a player is never permanently locked out.
- **Save waiting (R4-8).** `SaveData(player, opts?)`: opts `{WaitSeconds (default 5), RetryOnce (default false)}`. The `_saving` guard is NOT removed. PlayerRemoving waits up to 10 s, then waits once more (`RetryOnce`) before dropping. Dropped saves warn loudly.
- **Load failure and explicit reload (R5-1 — see R5 addendum §6).** A `GetDataStore` failure is a failed load, full stop: `LoadData` starts `loadOk` false and sets `_loadFailed[player] = (not loadOk)` — the session is unsaveable and `SaveData` refuses, so a recovered store can never be overwritten with defaults. `_sessionContested` is a different flag, set only in `finishSuccessfulLoad`'s lease path (another live server holds the lease). Recovery is through the explicit `DataService.RetryLoad(player)`: it re-attempts the load and only on a genuine successful load replaces the cache, clears `_loadFailed`, acquires the lease, merges sidecars and applies the bonus; any failure leaves the cache untouched and the session unsaveable; a healthy session is a no-op. It discards unsaved in-session progress by design and must not be called while the session holds unpersisted theft state.
- **Shutdown (R4-8, bounded by R5-7 — see R5 addendum §6).** `SaveAllForShutdown` spawns one task per player (each runs `SaveData` with `{WaitSeconds=5, RetryOnce=false}`), waits at most ~25 s for all, returns `{attempted, completed, saved}`; incomplete shutdown warns. BindToClose: hooks → `SaveAllForShutdown` → release leases. The parallel-vs-sequential bound is structural (parallel ≈ slowest single save; sequential ≈ sum) — the wall-clock budget is not measurable in Lune and needs a Studio test with 12 players under a degraded store. **R5-7:** the hook phase is now bounded — `RunShutdownHooks` spawns one task per player and waits at most `SHUTDOWN_HOOK_BUDGET_SECONDS = 10`, returning `{attempted, spawned, completed}`; `runPreSaveHooks` is per-player serialised (a second concurrent run waits, bounded 5 s, then returns `false` without re-running, so two hooks can never race on the same player's ownership transaction). Expected degraded total ≈ 16 s (7 s slowest hook + 9 s slowest save) for 1/6/12 players, inside the ~30 s budget; the two hard caps sum to 35 s, so in the pathological both-phases-saturated case the tail (lease release; leases self-expire in 90 s) can be cut.
- **Load-failed client notice (R4-8).** `GetSaveWarning(player)` returns `{Reason, Message}` or nil; `GameManager.onPlayerAdded` fires the `SaveWarning` remote right after `GetOrLoad`; `HUDController` shows a persistent red banner (never auto-hides) stating plainly that progress will NOT be saved this session and to rejoin. `SaveData` still refuses to overwrite the genuine profile when loading fails.
- `ReturnStolen` never saves inside the pre-save hook: a `_preSaveHookDepth` counter (set in `HandlePlayerLeaving`, pcall-wrapped, decremented on both paths) makes it skip its save-verify block there and rely on the escrow park + the coordinated leave/shutdown save. Live paths (drop/death/watchdog/rejoin) are unaffected.
- **Coin reservation (R4-3).** `ReserveCoins` / `ReleaseReservation` / `GetReservedCoins` / `GetSpendableCoins` (balance − reserved, floor 0). `AddCoins` negative amounts clamp at the reserved total, not zero; credits unaffected. `commitPendingPayment` reserves `payable` under `"reward:"..instanceId` before the verified save; reserve failure is fail-closed (un-pay at once, entry stays pending); save success releases; save failure releases FIRST then subtracts exactly. Every debit route judges affordability on spendable coins: `BaseService.UpgradeBase` + `UpgradeBrainrot`, `ConveyorService.BuyItem`, `EconomyService.BuyCharacter`, `RaidService.ActivateShield` + `TriggerLockdown`, `LaboratoryService` Evolve/Trait/AlternateForm, `AbilityService.UnlockPower`. **Follow-up (closed):** `FusionService.luau` was the last direct-assignment debit; it now judges affordability on `spendableCoins` and charges/refunds through `DataService.AddCoins` — no direct-assignment coin debit remains in the tree (test 10, 44/44, with a negative control failing exactly checks 37, 38, 42, 43 on the old code).
- **Session-health gates on ownership operations (R5-2 — see R5 addendum §6).** Steals, deliveries and place/store operations are refused in unhealthy sessions. `RaidService.checkSessionHealth` checks (1) the local R5-4 reason API `GetSaveBlockedReason` (`load_failed` / `session_contested` / `session_lost`) and (2) a proof against the STORED lease via `DataService.AcquireSessionLease`, fail-closed; it gates `StealBrainrot` (before the channel and again after it, before `removePlaced`) and `ConfirmDelivery` (before the escrow invalidation, for thief and online victim — a refused delivery parks no tombstone). `BaseService` has a local-only `sessionBlockedReason` gate on `PlaceBrainrot` / `StoreBrainrot` (whole-record reinsert restores stay exempt). Recovery paths (`ReturnStolen`, `RecoverStaleTransit`, `RecoverOnRejoin`, `RecoverPendingRewards`) are deliberately UNGATED — they restore ownership and must still run in unhealthy sessions.
- **Spendable-coins Rebirth/Prestige (R5-6 — see R5 addendum §6).** Rebirth and Prestige are R4-3 spending routes too: the coin requirement is judged on spendable coins (`ProgressionService.spendableCoins`), and the reset lands on `StartingCoins` + every reserved coin (`resetCoins`), so a pending reward commit open in the save window survives the reset (success keeps it, rollback subtracts it exactly). No economy values changed.

## 7. What is still NOT durable

- **R6 is not fixed.** A crash after an in-memory commit but before any save still loses the commit for non-ledgered state (ordinary earnings, XP, unlocks — up to one 60 s autosave interval). Theft items are covered by the ledger/escrow; the reconciler voids an unpersisted delivery conservatively.
- **Load-failed sessions** play on defaults with saves refused by design; a full session's earnings can be lost with only a server `warn`. **R4-8 narrows the user-facing gap:** the player now sees a persistent client-facing `SaveWarning` banner stating plainly that progress will NOT be saved this session and to rejoin. The durability hole itself is unchanged.
- **Cross-server behaviour is simulated, not proven live.** Keys are per-`UserId` and a player is in one server at a time; the R4-7 session lease (90 s TTL, tested in simulation with two module instances sharing one stub store) now prevents a second server silently overwriting the first server's newer data. Real multi-server Roblox behaviour is not tested.
- **Legacy InTransit records without `StolenFromUserId`** are no longer stuck forever: R4-10 adds a controlled server-authorized admin recovery (`RaidService.RecoverLegacyRecord`, explicit operator + target + instance + owner, exactly-one-owner check, no remote wired to it). No automatic recovery is attempted — the owner is never guessed.
- **No Studio playtest or real production DataStore test** has been run against any of this. All verification is Lune/harness-level with a stubbed DataStore API that models the contract.

## R5 addendum (2026-11-20, R5 docs closer)

What R5 changed about this model. All line numbers are current-source values, verified by grep against `src/` on 2026-11-20. The corrected paragraphs above (§1, §4, §5, §5a, §5b, §6) are the authoritative statements; this addendum collects the R5 rules in one place with their evidence (tests in `scripts/phase1-tests/r5-transactions/`, run via `run.sh` / `run_06.sh`).

### §5a — R5-5: no-store fail-closed rule

`DataService.InvalidateReturnEscrow` (1479) used to return success when `GetDataStore` failed to provide a usable store — claiming "nothing stale" without reading anything. That is the fail-open: a delivery could commit while a stale return the server could not see still existed in the victim's sidecar, producing a second owner on rejoin. The no-store branch now returns `(false, false, "datastore unavailable", nil)` (1491). A missing store is not an empty sidecar; the delivery is refused exactly as for any other unpersistable invalidation (transit live, no reward, no tombstone). `ConfirmDelivery` needed no change — its wrapper already fails closed. ### §5a / §5 — R5-2: §D interleaving shift (tombstone can supersede the FRESH return)

The return still wins the delivery (the delivery is refused with `"theft resolved during delivery"`), and the victim still holds the Brainrot in memory — the normal path is proven: the victim's leave save lands the returned Brainrot durably (test 02 §D, new check `SaveData(victim) == true` + stored key holds it). ### §5b — R5-3: void durability

- `DataService.RecordRewardVoidForInstance` (1591) parks an instance-level tombstone `{Voided=true, VoidInstance=true, TxId="void-inst-<instanceId>"}` in the thief's pending sidecar, plus per-TxId void entries for TxIds known from the cache or a best-effort sidecar read (a failed read never fails the void). - `RaidService.persistVoid` (2727) is the two-leg durability: leg 1 = park the tombstone; leg 2 = a main-profile save persisting the void ledgers (`VoidedRewardInstances` / `VoidedRewardTxns`). Durable iff either leg landed. The save leg is skipped inside the pre-save hook (`_preSaveHookDepth > 0`), where the coordinated leave save is the single save owner.
- `voidPendingRewardsForInstance` (2762) returns `(voidedTxIds, durable)` and has NO early return when the cache holds no entry — the Qwen defect was exactly that early return. `RetryPendingVoids` (2846) retries with the same stable identifiers.

### §6 — R5-4: lease rule correction

The R4 rule ("a failed lease read does not block — falls back to the cached lease") is superseded. `checkSessionLease` (544) verifies ownership against the STORED lease on every check; a failed read is resolved by an atomic proof — the same conditional `UpdateAsync`, whose RESULT names the owner: this server proves ownership (save proceeds — the R4 test-06 healthy-owner case now goes through the proof path, not the blind fallback), another live owner proves loss (sticky `_sessionLost`), a failed proof refuses THAT save attempt only (no sticky flag; recorded in `_leaseCheckUnverified`, 143, cleared in `PlayerRemoving`). `acquireSessionLease` (453) returns `(acquired, result)`; `tryAcquireLease` (497) marks lost when the acquire proves another live owner; `refreshSessionLease` (620) extends the local cached expiry ONLY when an `UpdateAsync` result confirms this server owns the lease, returns bool; `GetSessionLeaseState` (703) exposes the contested state for the R5-2 gates. `SaveData` (2078) revalidates after the `_saving` wait (~2144) and immediately before every `SetAsync` retry (~2160, clearing `_saving` on refusal). Exact remaining partition boundary: a failed lease read AND a failed proof in the same check refuses that attempt only; two servers can both be refused (never both write) but a single server cannot prove ownership during a total DataStore outage, so saves pause until the store recovers (liveness, not safety, is what the partition costs). Test 04 32/32; mutant m04 12/12 overwrites the newer profile under the old code.

### §6 — R5-1: RetryLoad, and `_loadFailed` vs `_sessionContested`

`LoadData` (1984) sets `_loadFailed[player] = (not loadOk)` (2002) — a `GetDataStore` failure is a failed load, the session is unsaveable, and `SaveData` refuses, so defaults can never overwrite a genuine profile after recovery. `_sessionContested` is a different flag, set ONLY in `finishSuccessfulLoad`'s lease path (1925: another live server holds the lease; cleared 1936 on a later load that acquires it). `RetryLoad` (2037) is the explicit reload path: re-attempts the load, and only on a genuine successful load replaces the cache, clears `_loadFailed` (2058), acquires the lease, merges sidecars and applies the bonus; any failure leaves the cache untouched; a healthy session is a no-op.
